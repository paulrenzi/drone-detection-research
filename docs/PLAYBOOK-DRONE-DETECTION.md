## 2. Architecture

### 2.1 The packet (I1 + I1a)

40 bytes on air: `[8 B nonce][16 B ciphertext][16 B GCM tag]`, AES-128-GCM.

- **Nonce (I1a):** `[u16 sender_id][u16 boot][u32 counter]`, little-endian.
  IV (12 B) = `key[0:4] + nonce`.
- **boot** lives in NVS (namespace `lora_nonce`, key `boot`). At start-up the firmware
  reads it, adds 1, and **persists the new value before the first transmit**. If the write
  fails, or boot would reach 0xFFFF, the listener refuses to transmit (task suspended).
  This is deliberate: a repeated (key, IV) breaks GCM completely.
- **counter** starts at 0 each boot. After 0xFFFFFFFF the transmit state moves to
  boot + 1 with counter 0 and tells the caller to persist the boot (`persist_boot`).
- **Plaintext (16 B, LE):** listener_id u16, type, age_ds u16, hops, f0_bin, rms_db, conf,
  dur_s, vbat_cv, temp_c, rssi_hint, tag_boot, tag_ctr, flags.
- **Replay check:** a receiver accepts only a strictly newer (boot, counter) per sender.
- **The nonce's sender_id must equal the plaintext listener/device id**, or the packet is
  rejected.

**Why the fix existed:** Batear's original nonce could repeat across reboots under the
same key (the defect is described in `tripwire-firmware/main/lora_crypto.h`). Fixed in
`tripwire-firmware` 9503e25, in both the detector and the gateway.

### 2.2 Relaying (I2)

- A relay **re-encrypts under its own nonce** (its own sender_id, boot, counter). So a
  relayed copy does *not* carry the origin's nonce.
- The alert's identity survives in the plaintext: **dedup key = (origin listener_id,
  tag_boot, tag_ctr)**, where the tag bytes are the origin's boot and counter, low byte
  each. This closed a spec gap: I2 rule 2 used to dedup on the origin's nonce, which a
  relay can't see.
- On relay: age saturates at 65535, hops capped at `TW_HOPS_MAX` (63; `HOPS_MAX` in
  Python), `rssi_hint = max(hint, clamp(-rssi, 1, 255))`.
- **Relay rule:** relay once; wait 100–600 ms, shorter the weaker the alert was heard,
  plus up to 50 ms jitter; **cancel only after hearing two more copies** (Paul,
  2026-10-19; Meshtastic cancels on one); check the channel before sending and re-draw
  the wait if busy.
- **Hop cap is 63** everywhere: the spec (`build-software.md` rule 4), `TW_HOPS_MAX`,
  Python `HOPS_MAX`, and the simulator's default `hop_limit` (raised 2026-10-19,
  firmware 692b51d, tools da93d01). The `relay_saturates` vector holds hops at 63.

### 2.4 The relay simulator

`tripwire-tools/tripwire/relaysim.py`, a discrete-event model of one alert flooding down
a line of listeners to an edge receiver (`EDGE = -1`, never transmits).

- **Radio:** SX1262, SF10, 125 kHz, CR 4/5, 22 dBm, 40-byte packet; Semtech sensitivity
  formula; half-duplex; 6 dB capture.
- **Listening:** duty-cycled, each listener checks the channel every `cycle_ms` (1 s
  default). The preamble is sized to one cycle plus one check (1.07 s), so airtime is
  **1.5 s** per packet. A 16-symbol preamble would be 0.60 s but is mostly missed.
- **Path loss:** log-distance with per-link shadowing and per-packet fading.

  | Preset | PL at d0 | Exponent | Fitted to |
  |---|---|---:|---|
  | `forest_dense` | 127 dB at 70 m | 5.8 | T9 literature (Iova, Ferreira, Callebaut) |
  | `forest_light` | 127 dB at 70 m | 2.7 | same |
  | `open` | 127 dB at 500 m | 3.3 | same |
  | `meshtasticator` | 127.41 dB at 40 m | 2.08 | Meshtasticator defaults, used by the tests |

- **Rules (`RelayRule.kind`):** `weighted` (ours, I2), `random` (old uniform 100–600 ms),
  `meshtastic` (the firmware's client rule). `cancel_after=k` cancels after k duplicates;
  left at `None` it is the kind's own (`dups_to_cancel`): **2 for `weighted`/`random`,
  1 for `meshtastic`**, so the Meshtastic checks still model Meshtastic.
- `test_weighted_wait_takes_longer_hops_than_random` pins `cancel_after=1`: at 2 the hop
  gap is noise (1.96 vs 2.00 over 1,500 trials), so it can only see the mechanism at 1.
- **Meshtastic's rule as modelled** (read from its firmware source 2026-10-19): CWmin 3,
  CWmax 8, `CW = map(snr, -20, 10, 3, 8)` in integer arithmetic (truncates, does not
  clamp), wait `(2·CWmax + random(0, 2^CW))` slots, slot = `max(2.25, 4 + 0.5)·Tsym + 7.6 ms`
  (44.464 ms at SF10/125), channel check before transmit, cancel on duplicate, hop limit 3.
- Results come from `Line.run` → `Trial` and `sweep` → `Summary`.

## 3. Findings (model, not measurement)

From `tripwire-tools/reports/relay-sim-phase0.md` (400 trials per row). T9's field data
replaces these numbers when it exists.

- **Spacing for 90% delivery** from the far end of 20–30 listeners: dense forest ~100 m,
  light forest ~250 m, open ~1,200 m. A 20-listener dense-forest line is ~2 km.
- **Delay to the edge 15–40 s** at those spacings, ~2.3 s per hop. The listening cycle
  sets most of it: 0.25 s cycles cut the delay by ~40% at a battery cost T12 must measure.
- **Nearly every listener transmits once per alert** (17 of 20, 27 of 30, dense forest).
- **Hop cap 15 was too low** for 30 listeners in dense forest at 90 m: 62% vs 94% at 63.
- **The signal-weighted wait now leads random only slightly** (95% vs 92%, dense forest,
  80 m; 88% vs 54% under cancel-after-1). It still beats Meshtastic's client wait (78%,
  slower; 0.7–12 s waits at this slot time, tuned for chat).
- **Cancel-after-2 is the rule (Paul, 2026-10-19).** Cancel-on-one lost alerts: the
  front-most listener heard a copy from a listener *behind* it and cancelled, so nobody
  ahead was reached (15 of 20 failures traced). Two costs ~1.5× the transmissions for
  +7 to +19 points of delivery.

## 4. How to run and debug

### Reading a Saturday test's results (from any session, phone included)

The logger saves each session online as it goes, so nothing gets exported. No credential is needed:

```bash
curl -s https://tripwire-sessions.paulmichaelrenzi.workers.dev/sessions          # every session, newest first
curl -s https://tripwire-sessions.paulmichaelrenzi.workers.dev/sessions/latest   # the newest, in full
```

A session is `{session, gateway, saved_at, runs, events, raw}`. Each run already carries its summary (`heard`, `first_alarm_s`, `packets`, `rssi_median`, and so on), and speaker runs carry `level_dba`, `gain_db` and `cal_dba`. The pass mark is heard at 100 m emulated; under 60 m is a fail. The Worker is `worker/` (KV namespace `tripwire-sessions`, deploy with `CLOUDFLARE_WORKER_DEPLOY_TOKEN`). Reads and writes are open, so it holds test data only.

### C codec tests

🛑 **There is no C compiler on Paul's PC.** Run them in one of two places:

- GitHub CI: workflow `codec-host-test.yml` (installs `libssl-dev`, runs
  `make -C components/tw_codec/test`). ESP-IDF builds of all five roles (Batear's three
  plus `listener` and `edge`) run in `esp-idf-build.yml`.
- 🛑 `gh` in `tripwire-firmware` resolves to **Batear** (the `upstream` remote) by default.
  Always pass `-R paulrenzi/tripwire-firmware`.
- `ssh ubuntu@claude-dev` (gcc 11 + libssl-dev): clone or copy the repo there, then
  `make -C components/tw_codec/test`. 102 checks pass under ASan/UBSan.

### Changing the packet or the vectors

1. Change `tripwire/codec.py` **and** `components/tw_codec/tw_codec.c` together.
2. Regenerate: `python -m tripwire.vectors > vectors/i1_vectors.txt` (never edit by hand).
3. Copy the file to `tripwire-firmware/components/tw_codec/test/i1_vectors.txt`.
4. Python tests fail if the committed file differs from the generator, or if the two
   copies differ (when the firmware repo sits beside the tools repo).
5. `.gitattributes` keeps `*.txt` LF on every checkout; a CRLF copy would break the
   byte-identical check.

The vector file covers: seal (first boot, reboot, other listener same counter, last
counter in a boot, wrap to the next boot, other key), relay (hop 1, hop 2, saturation),
open_fail (tampering), tx (the nonce state machine) and replay. The test also asserts no
(key, IV) pair repeats anywhere in it.

**Prove a test can fail before trusting it:** mutating one vector byte fails both the C
(4 checks) and Python tests; that was checked 2026-10-19.

### Debugging the simulator

- Each simple case in `tests/test_relaysim.py` pins the path loss with `link_db` (no
  shadowing, no fading) so the expected answer is exact. Copy that pattern to isolate a
  behaviour.
- To see why an alert died, run one `Line.run(rng, origin)` and read `Trial.senders`
  (who transmitted, in order) and `Trial.reached`.
- A statistical test compares against an exact probability within 4 standard deviations.
  If one fails, first suspect the "exact" formula: the cluster test once failed because
  the formula ignored two nodes tying on a slot (they collide, nobody decodes, more relay).
